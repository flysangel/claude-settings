# sdd-grill

The maintainer has a requirement, usually vague. Your job is to turn it into a set of explicit decisions the
maintainer agrees with, by asking one question at a time, and then to have Spec Kit write those decisions down as
the project's constitution and one spec per feature. After that you stop: planning and implementation are separate
steps the maintainer starts.

Two things matter more than anything else here:

- **Nothing is written to the constitution or to `specs/` until the maintainer has confirmed a summary of all
  decisions.** Specs drive everything that follows, so a wrong rule written early gets copied into plans and code.
- **The documents are generated by Spec Kit's own skills (`speckit-constitution`, `speckit-specify`), never written
  by hand.** That keeps the files in the format Spec Kit expects and lets Spec Kit choose folder names and numbers.

You do the conversation. A small script does everything that has to be exact: checking the project, saving the
discussion so it can be resumed, and checking the generated files afterwards.

## The script

Run it from the project's root directory (the directory this session works in):

```text
uv run "${CLAUDE_SKILL_DIR}/scripts/sdd_grill.py" <command>
```

| Command | What it does |
|---|---|
| `check` | Reads the project: is Spec Kit there, is there a constitution, which specs exist, is there saved progress and what changed since. Writes nothing. |
| `save` | Reads the full progress as JSON on stdin, validates it, and writes `.specify/sdd-grill/progress.json`. |
| `verify` | After generation, checks the constitution and the new specs against the confirmed summary. Writes nothing. |
| `focus` | After `verify` passes, points `.specify/feature.json` at the first new spec. |
| `clear` | Removes the saved progress. |

Every command prints one JSON object on stdout. When it fails, the object has an `error` field with one English
sentence (also printed on stderr). Exit codes: `0` success, `1` failure (invalid input, failed checks, or a conflict),
`3` Spec Kit is missing or incomplete (only `check`). Read the JSON rather than guessing from the exit code alone.

The progress lives in `.specify/sdd-grill/`, a folder that only sdd-grill uses. It contains its own `.gitignore`, so
the progress never shows up in `git status` and is never committed.

## Start

1. Run `uv run "${CLAUDE_SKILL_DIR}/scripts/sdd_grill.py" check` before you ask the maintainer anything. It is
   read-only, and its answer decides whether you can continue at all.
2. If the command itself cannot run because `uv` is not installed (for example "command not found"), tell the
   maintainer that sdd-grill needs `uv`, and stop. Do not try to work around it, for example by keeping the progress
   yourself.
3. If `check` ends with exit code 3, Spec Kit cannot be used in this project:
   - `speckit` is `"missing"`: the project has no `.specify/` folder. Tell the maintainer that Spec Kit is not set up
     and ask them to run `/sdd-init` and then `/sdd-grill` again.
   - `speckit` is `"incomplete"`: `.specify/` exists, but files that Spec Kit needs to generate a constitution and
     specs are missing, which may mean Spec Kit changed incompatibly. Report this and list the paths in `missing`.

   In both cases stop there, without asking any question about the requirement. Do not run `/sdd-init` yourself, and
   do not create or change anything in `.specify/` or in the `speckit-*` skills to make it work: those files belong
   to Spec Kit and are only ever produced by its official tools.
4. Look at `progress`:
   - `"conflict"`: `.specify/sdd-grill/` holds files that sdd-grill did not create. Tell the maintainer, ask them to
     move those files out of that folder, and stop. Do not delete or change them.
   - `"unreadable"`: there is a progress file, but it is damaged or comes from an incompatible version. Tell the
     maintainer, and ask one question: clear it and start over (recommended, since it cannot be resumed), or stop
     and leave it as it is. To clear it, run `uv run "${CLAUDE_SKILL_DIR}/scripts/sdd_grill.py" clear`, then
     continue as for `"none"`.
   - `"present"`: there is a discussion to resume. Go to "Resume".
   - `"none"`: a new discussion.
5. For a new discussion you need a requirement: the text the maintainer gave after `/sdd-grill`, or, if this skill
   was chosen without the command, what the maintainer said they want. If there is no requirement, ask the
   maintainer to describe what they want to build or add, and do nothing else until they answer.
6. Keep the rest of the `check` output in mind; it saves you questions:
   - `constitution`: `"written"` means the project already has a constitution, whose principles are already decided.
     `"missing"` or `"template"` means there is none yet.
   - `specs`: the specs that already exist (`dir` and `number`). New specs will be numbered after them, and new
     features can depend on them.
   - `numbering`: how Spec Kit numbers new specs (`"sequential"` or `"timestamp"`). You never choose numbers, but it
     tells you what to expect.

## Rules for questioning

These rules apply to every question you ask, in every part of the discussion.

- **Find out what you can before asking.** Before the first question, read what the project already says: the
  constitution (`.specify/memory/constitution.md`), the existing specs (`specs/*/spec.md`), the README, and enough of
  the code and configuration to know what exists. Anything you can learn there, adopt it and say briefly where it
  came from; do not ask the maintainer about it. Existing decisions in the constitution and specs count as decided:
  do not ask about them again.
- **Derive the questions from the requirement and the project.** Look for the decisions the requirement leaves open
  that would change what gets built or how it is judged. Do not work through a fixed list of questions or a generic
  checklist: every question must be traceable to something specific in the requirement or the project, so that the
  maintainer can see why you are asking it.
- **One question per message, with a recommendation.** Ask with the `AskUserQuestion` tool, one question per call.
  Put your recommended answer as the first option, mark it "(Recommended)", and give the reason in its description;
  the other options should be real alternatives. If `AskUserQuestion` is not available (it is not in your tools, the
  call is refused, or it fails), ask in plain text instead, with the same shape: still one question, your
  recommendation first with its reason, the alternatives after it, and then wait for the answer.
- **Do not accept vague answers.** If an answer does not let you judge whether a concrete approach would satisfy it
  ("it should be fast", "keep it simple", "secure enough"), keep asking until it does: fast for which action, how
  fast, measured how. Offer a concrete recommended value each time.
- **Point out contradictions.** If an answer contradicts an earlier decision, quote both sides and ask the maintainer
  which one wins; then update the progress to match. If an answer conflicts with a principle of the existing
  constitution, name the principle and ask whether to amend the principle or adjust the requirement.
- **Leave technology choices to the plan.** Languages, frameworks, libraries, databases, hosting and similar choices
  belong to the plan, not to the spec. When one comes up, record it in `for_plan` (with the feature it concerns, or
  `null` for the whole project), tell the maintainer it is left for the plan, and move on without discussing or
  recommending it. If the maintainer states it as a firm constraint, record their words in `for_plan` as they said
  them.
- **Never record secrets.** If the maintainer gives you a password, key, token or a connection string with
  credentials, do not record the value anywhere: not in the progress and not in what you pass to Spec Kit. Record
  only what is needed ("needs an API key for the payment service, supplied by the maintainer at run time"), and tell
  the maintainer that the value itself was not recorded.
- **Deferring is an answer.** If the maintainer wants to decide something later, record it in `deferred` with the
  reason, and continue.
- **Stopping early.** If the maintainer wants to stop, make sure the latest state is saved, present a summary of
  what is decided so far (in the shape described in "Summary and confirmation", plus what is still open), tell them
  that running `/sdd-grill` again continues from here, and stop. Do not generate anything.

## Order of the discussion

Go through four stages, in this order. The current stage is the `stage` field of the progress, so that a resumed
discussion knows where to continue.

1. **Constitution principles** (`"principles"`). The rules every feature must follow: quality bar, supported
   platforms, testing, what the project must never do, documentation language, and how the constitution itself is
   amended (governance). Ask only about principles the requirement actually raises.
   - No constitution yet (`constitution` is `"missing"` or `"template"`): set `constitution.action` to `"create"`
     and record each agreed principle and governance rule.
   - The project already has a constitution: its principles are decided. Only deal with what the new requirement
     adds to them or conflicts with. If the maintainer agrees to change the constitution, set `action` to `"amend"`
     and record only the additions and changes; otherwise set it to `"keep"` and leave `principles` and `governance`
     empty.
2. **Feature list and dependencies** (`"features"`). Split the requirement into features, each one becoming one
   spec. Propose the split, then settle it with the maintainer question by question. Order the list so that every
   feature comes after the features it depends on; that order becomes the order of the spec numbers and the
   suggested order of work. A feature may also depend on an existing spec, given as its folder (for example
   `specs/003-sdd-init`, taken from `check`'s `specs`).
3. **Each feature in turn** (`"feature"`). Take one feature at a time, in list order, and settle its usage
   scenarios, its scope (what is in and what is out), and its edge cases. Set `current_feature` to the feature's id
   and its `status` to `"discussing"`; when it is settled, set `status` to `"decided"` and move to the next feature.
4. **Summary** (`"summary"`). When every open point is decided or deferred, go to "Summary and confirmation".

If a later answer changes an earlier stage (a new feature appears, a principle turns out to be needed), update that
part of the progress and keep the ordering rules above.

**Language.** Talk with the maintainer in the language their own settings ask for. The generated constitution and
specs use the language of the project's existing documents (constitution, specs, README). If that cannot be
determined, use Traditional Chinese, keeping normative keywords such as MUST and SHOULD in English. Record the
language in `language` (for example `"zh-TW"`) as soon as you know it; it must be set before the summary is
confirmed.

## Saving progress

After every decision, save the full progress: after each answered question, each deferral, each item added to
`for_plan`, and each change of stage. The maintainer may leave at any moment, and anything not saved is lost.

Pass the whole progress as JSON on stdin, every time (the script replaces the file; it does not merge):

```text
uv run "${CLAUDE_SKILL_DIR}/scripts/sdd_grill.py" save <<'SDD_GRILL_PROGRESS'
{ ...the full progress... }
SDD_GRILL_PROGRESS
```

The progress has exactly these fields; all strings must be non-empty, and no other fields are allowed:

| Field | Value |
|---|---|
| `schema` | `1` |
| `tool` | `"sdd-grill"` |
| `requirement` | The maintainer's requirement, in their words. |
| `language` | Language of the generated documents, such as `"zh-TW"`, or `null` while unknown. |
| `phase` | `"discussing"`, or `"confirmed"` once the maintainer has confirmed the summary. |
| `stage` | `"principles"`, `"features"`, `"feature"` or `"summary"`. |
| `current_feature` | The id of the feature being discussed when `stage` is `"feature"`; otherwise `null`. |
| `constitution` | `{"action": "create" \| "amend" \| "keep", "principles": [{"title": "...", "rules": ["..."], "rationale": "..." or null}], "governance": ["..."]}` |
| `features` | In dependency order: `{"id": "...", "title": "...", "depends_on": [...], "status": "pending" \| "discussing" \| "decided", "decisions": [{"topic": "...", "decision": "..."}], "spec_dir": null}` |
| `deferred` | `{"item": "...", "reason": "...", "feature": "<id>" or null}` |
| `for_plan` | `{"item": "...", "feature": "<id>" or null}` |

A feature `id` is lowercase letters and digits joined by single hyphens (`expense-entry`) and is unique.
`depends_on` lists ids of features earlier in the list, or folders of existing specs (`specs/<name>`, containing a
`spec.md`). `spec_dir` stays `null` until the document is generated. The script adds `saved_at`, `fingerprint` and
`baseline` itself; leave them out.

On success the output is `{"saved": ".specify/sdd-grill/progress.json", ...}`. If `save` fails, nothing was written:

- `progress is not valid JSON: ...` or `progress is invalid at <field>: <reason>`: fix that field and save again.
- `progress at <field> looks like a secret; ...`: rewrite that field as a description of what is needed, without
  the value, tell the maintainer, and save again.
- `.specify/sdd-grill/ holds files sdd-grill did not create; ...`: tell the maintainer, as in "Start", and stop.

If you cannot get a save to succeed, tell the maintainer what the error says and stop rather than continue with
progress that is not saved. Write the progress only through `save`: never create, edit or delete files in
`.specify/sdd-grill/` in any other way, because the script is what keeps that folder valid and out of git.
