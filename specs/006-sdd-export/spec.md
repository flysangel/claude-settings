# Feature Specification: sdd-export 從舊專案匯出養分

**Feature Branch**: `006-sdd-export`

**Created**: 2026-11-19

**Status**: Draft

**Input**: User description: "在舊專案執行 /sdd-export，把需求與經驗教訓整理成一份「養分」，留在舊專案的專用目錄，供新專案重生時使用；沒有 spec 時從程式碼導出需求。"

## User Scenarios & Testing *(mandatory)*

專案的重生如同鳳凰浴火：每一代繼承的需求、這一代新增的需求，以及這一代學到的教訓，
都成為下一代的養分。本功能負責在舊專案產生這份養分；在新專案使用它屬於 007 sdd-rebuild。

### User Story 1 - 把已有 spec 的專案匯出成養分 (Priority: P1)

維護者在一個已有 constitution 與 spec 的專案輸入 `/sdd-export`。Claude 整理出原則、各功能的需求與相依關係，
提出經驗教訓的草稿，維護者確認後，養分寫入舊專案內的專用目錄。

**Why this priority**: 這是重生循環的起點，也是最常見的情況：以 SDD 開發的專案本來就有 spec。

**Independent Test**: 在有 constitution 與 3 份 spec 的專案執行，確認養分包含全部原則與 3 個功能的需求，
不含 plan、tasks 與程式碼，且除了專用目錄之外專案沒有任何變化。

**Acceptance Scenarios**:

1. **Given** 專案有 constitution 與 spec，**When** 執行 `/sdd-export`，
   **Then** Claude 提出養分草稿：constitution 原則、每個功能的需求與相依關係、經驗教訓，以及世代資訊。
2. **Given** 草稿已呈現，**When** 維護者尚未確認，**Then** 專案內沒有任何檔案被寫入。
3. **Given** 維護者確認草稿（可逐項修改或刪除），**When** Claude 寫入養分，
   **Then** 養分只出現在舊專案內一個專用的固定目錄，專案既有的檔案完全不變。
4. **Given** 養分已寫入，**When** 檢視內容，
   **Then** 其中沒有 plan、tasks 與程式碼，需求只描述使用者需求與可驗收的行為，不描述現行實作。
5. **Given** 養分已寫入，**When** 流程結束，
   **Then** Claude 說明養分的位置、可以提交到 repo，以及下一步是在新專案執行 `/sdd-rebuild`。

---

### User Story 2 - 沒有 spec 時從程式碼導出需求 (Priority: P1)

舊專案沒有 spec，或 spec 沒有涵蓋全部功能。Claude 讀取程式碼，導出目前實際的行為作為需求，
把疑點另外列出，由維護者逐項決定要不要納入。

**Why this priority**: 許多值得重生的專案正是沒有 spec 的舊專案；沒有這個能力，它們無法進入循環。

**Independent Test**: 在只有程式碼、沒有 Spec Kit 的專案執行，確認每項導出的需求都附有依據檔案，
疑點獨立列出，專案除專用目錄外沒有任何變化，也沒有被導入 Spec Kit。

**Acceptance Scenarios**:

1. **Given** 專案沒有 spec 也沒有導入 Spec Kit，**When** 執行 `/sdd-export`，
   **Then** Claude 讀取文件、設定、測試與程式結構，提出候選功能清單與每個功能的需求，不要求先導入 Spec Kit。
2. **Given** Claude 提出導出的需求，**When** 檢視草稿，
   **Then** 每項需求只描述程式碼目前實際的行為，並附上依據的檔案；無法確定的標為待確認。
3. **Given** Claude 發現疑似 bug、文件與程式碼矛盾或可改進之處，**When** 呈現草稿，
   **Then** 這些另外列出，不混入需求；維護者逐項決定納入、修改或捨棄。
4. **Given** 專案的 spec 只涵蓋部分功能，**When** 執行 `/sdd-export`，
   **Then** 已有 spec 的功能以 spec 為準，其餘功能從程式碼導出，並標明各自的來源。
5. **Given** 導出進行中，**When** 檢查 Claude 的動作，
   **Then** 全程只讀取專案，沒有執行建置、測試或其他會在專案內產生檔案的指令。

---

### User Story 3 - 帶出經驗教訓 (Priority: P2)

養分不只是需求。Claude 從專案的文件與歷史整理出這一代的重要決定與理由、踩過的坑、後來被推翻的做法，
維護者確認後一併寫入，讓下一代比這一代更好。

**Why this priority**: 只帶需求的話，重生只是複製；教訓才是讓下一代改進的養分。它建立在前兩個情境之上。

**Independent Test**: 在有修訂紀錄的專案執行，確認草稿列出可追溯到專案內容的教訓，
維護者刪除其中一項後，寫入的養分不含該項。

**Acceptance Scenarios**:

1. **Given** 專案有文件與歷史紀錄，**When** Claude 整理經驗教訓，
   **Then** 草稿分為重要決定與理由、踩過的坑、被推翻的做法，每項附上依據；沒有依據的標為待確認。
2. **Given** 經驗教訓草稿已呈現，**When** 維護者修改、補充或刪除項目，
   **Then** 寫入的養分反映維護者確認後的內容。
3. **Given** 專案找不到任何可作為教訓的依據，**When** Claude 整理，
   **Then** 說明沒有找到，並請維護者決定是否口頭補充，不自行編造。

---

### User Story 4 - 世代延續 (Priority: P2)

這個專案本身是從上一代重生的。再次匯出時，養分同時包含繼承自前代的需求與這一代新增的需求，
並記錄每項需求來自哪一代。

**Why this priority**: 這讓重生成為可重複的循環，而不是一次性的搬遷。

**Independent Test**: 在一個由 sdd-rebuild 建立、之後又新增了 2 份 spec 的專案執行，
確認養分的世代編號加一，繼承的需求保留原本的來源世代，新增的 2 項標為這一代。

**Acceptance Scenarios**:

1. **Given** 專案留有上一代的世代紀錄，**When** 執行 `/sdd-export`，
   **Then** 養分的世代編號比上一代大一，每項需求標明來自哪一代。
2. **Given** 專案沒有世代紀錄，**When** 執行 `/sdd-export`，**Then** 這個專案視為第一代。
3. **Given** 前代的經驗教訓仍然適用，**When** 產生養分，
   **Then** 它們與這一代的教訓一併帶出，並標明來源世代。
4. **Given** 專案已有先前匯出的養分，**When** 再次執行 `/sdd-export`，
   **Then** 更新同一份養分以反映目前的狀態，不產生第二份；更新前同樣需要維護者確認。

### Edge Cases

- 專案很大或是 monorepo：先列出主要區塊，請維護者縮小範圍，不一次讀完。
- 專案內容太少，無法提出有依據的需求：說明原因並停止，不寫入養分。
- 相依套件與建置產物（例如第三方套件目錄）：排除在外，它們不是這個專案的功能。
- 專案內有機密檔案或檔案中出現機密值：不開啟機密檔案；機密值不出現在對話、草稿與養分中，只記錄位置。
- spec 與程式碼矛盾：把兩邊都列出，由維護者決定，不自行選擇。
- 專用目錄已存在但內容不是本功能產生的：停止並回報，不覆蓋。
- 專案是唯讀的或不屬於維護者：無法寫入時回報原因，草稿內容仍呈現給維護者。
- 維護者中途結束：不寫入任何內容。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 維護者 MUST 能在舊專案以 `/sdd-export` 產生養分；舊專案 MUST NOT 需要先導入 Spec Kit。
- **FR-002**: 養分 MUST 包含：constitution 原則、各功能的需求與相依關係、經驗教訓、每項需求來自哪一代、世代編號。
- **FR-003**: 養分 MUST NOT 包含 plan、tasks 與程式碼。
- **FR-004**: 需求 MUST 只描述使用者需求與可驗收的行為，MUST NOT 描述現行的實作方式。
- **FR-005**: 專案有 spec 的功能 MUST 以 spec 為來源；沒有 spec 或 spec 不足的功能 MUST 從程式碼導出。
- **FR-006**: 從程式碼導出的需求 MUST 只描述程式碼目前實際的行為，且每項 MUST 附上依據的檔案；
  無法確定的 MUST 標為待確認，MUST NOT 寫成事實。
- **FR-007**: 疑似 bug、文件與程式碼的矛盾、改進建議 MUST 與需求分開列出，並由維護者逐項決定是否納入。
- **FR-008**: 本 skill MUST 全程只讀取舊專案的既有內容，MUST NOT 執行建置、測試或其他會產生檔案的指令。
- **FR-009**: 經驗教訓 MUST 由 Claude 從專案文件與歷史整理成草稿，分為重要決定與理由、踩過的坑、被推翻的做法；
  沒有依據的內容 MUST NOT 自行編造。
- **FR-010**: 所有內容 MUST 先以草稿呈現，維護者確認後才寫入；確認前 MUST NOT 寫入任何檔案。
- **FR-011**: 養分 MUST 寫在舊專案內一個專用的固定目錄，可以隨 repo 提交；
  本 skill MUST NOT 修改或刪除該目錄以外的任何檔案。
- **FR-012**: 專案留有上一代的世代紀錄時，養分 MUST 同時包含繼承的需求與這一代新增的需求，
  保留繼承項目原本的來源世代，並把世代編號加一；沒有世代紀錄時視為第一代。
- **FR-013**: 前代仍然適用的經驗教訓 MUST 一併帶出並標明來源世代。
- **FR-014**: 再次匯出 MUST 更新同一份養分，MUST NOT 產生第二份。
- **FR-015**: 本 skill MUST NOT 開啟機密檔案；機密值 MUST NOT 出現在對話、草稿與養分中。
- **FR-016**: 專案過大時 MUST 先請維護者縮小範圍；內容不足以提出依據時 MUST 說明原因並停止。
- **FR-017**: 相依套件與建置產物 MUST 排除在導出範圍之外。
- **FR-018**: 完成後 MUST 回報養分的位置、納入與捨棄的項目，以及下一步是在新專案執行 `/sdd-rebuild`。
- **FR-019**: 同一個舊專案在 Windows 與 Linux 產生的養分 MUST 可以互通：在一個平台匯出，另一個平台可以直接讀取。
- **FR-020**: 本 skill MUST 以英文撰寫，其資料夾 MUST 包含一份繁體中文的 README 簡述。

### Key Entities

- **養分**: 一代專案留給下一代的內容，由原則、需求、相依關係、經驗教訓與世代資訊組成。
- **需求項目**: 一個功能的使用者需求與可驗收行為，帶有來源（spec 或程式碼）與來源世代。
- **經驗教訓**: 重要決定與理由、踩過的坑、被推翻的做法，各帶有依據與來源世代。
- **疑點**: 疑似 bug、矛盾與改進建議；經維護者決定後才可能成為需求或教訓。
- **世代紀錄**: 專案是第幾代、它繼承了哪些需求；由 007 sdd-rebuild 留在新專案，供本功能讀取。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 匯出後，舊專案在專用目錄以外被修改或刪除的檔案數量為 0。
- **SC-002**: 維護者確認之前，被寫入的檔案數量為 0。
- **SC-003**: 從程式碼導出的需求中，100% 附有依據檔案或被標為待確認。
- **SC-004**: 養分中出現的機密值數量為 0，plan、tasks 與程式碼片段的數量為 0。
- **SC-005**: 已有 spec 的專案，其 100% 的功能都出現在養分中，除非維護者明確捨棄。
- **SC-006**: 連續經過三代重生後，第一代的需求在第三代的養分中仍可追溯到第一代。
- **SC-007**: 在一個平台匯出的養分，於另一個平台不經任何轉換即可被 sdd-rebuild 讀取。

## Assumptions

- 養分的檔案格式與專用目錄的名稱由 plan 決定。
- 對話式流程的自動測試能涵蓋的範圍由 plan 決定；依 constitution，本功能仍 MUST 有自動測試並在兩個平台的 CI 通過。
- 維護者指定的限制：產出只有 skill 文件或 script；Python script 一律用 uv 執行。
- 「只替既有專案補上 spec、不重生」不是本功能的目的；本專案不提供獨立的導出 skill。
- 是否把養分提交到 repo 由維護者決定；本 skill 不代為提交到舊專案以外的地方。
- 跨機器搬運養分的方式是取得舊專案的 repo。
- 本功能依賴 001 部署工具把 skill 安裝到機器上；它在舊專案執行，不依賴 003 sdd-init。
