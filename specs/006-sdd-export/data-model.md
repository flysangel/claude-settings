# Data Model: sdd-export

養分、世代紀錄、草稿、讀取範圍與驗證規則的定義。決定與理由見 [research.md](./research.md)（R2 至 R6）；
指令的輸入與輸出見 [contracts/cli.md](./contracts/cli.md)。

**本文件同時是 007 sdd-rebuild 的契約**：「養分（`nutrients.json`）」是 007 要讀取的格式；
「世代紀錄（`lineage.json`）」是 007 要寫入、006 要讀取的格式。改動這兩節的任何欄位或規則 MUST 提高 `schema`。

## 共通的序列化規則

養分與世代紀錄都適用：

- UTF-8，沒有 BOM；換行為 LF；縮排 2 個空白；非 ASCII 字元不跳脫（`ensure_ascii=False`）；結尾一個換行。
- 物件的鍵依本文件列出的順序；陣列保留給定的順序。
- 路徑一律相對於專案根目錄、以 `/` 分隔，不以 `/` 或 `./` 開頭，不含 `..`，不含磁碟代號；MUST NOT 出現絕對路徑。
- 讀取時先把 CRLF 正規化成 LF 再解析與計算雜湊；兩個平台讀到的內容相同。
- 讀取者遇到 `schema` 大於自己認得的版本時 MUST 停止並說明需要更新 skill；MUST NOT 猜測內容。
- 識別字 `id` 的格式：`^[a-z0-9]+(-[a-z0-9]+)*$`，長度不超過 64。
- 字串欄位 MUST NOT 是空字串（除非另外註明），MUST NOT 含程式碼區塊（三個以上的 `` ` `` 或 `~` 開頭的行）。
- 物件 MUST NOT 有本文件沒有列出的鍵（擋下 `plan`、`tasks`、`code` 這類欄位）。

## 專用目錄：`.sdd-export/`

位於舊專案根目錄，只屬於 sdd-export。腳本只會在這裡寫入以下三個檔案（與寫入時同目錄的暫存檔），從不刪除任何檔案。

| 檔案 | 內容 |
|---|---|
| `nutrients.json` | 養分本體，唯一的資料來源 |
| `README.md` | 由 `nutrients.json` 產生的可讀版本 |
| `.gitattributes` | 固定兩行：`# Created by sdd-export; keeps these files LF on every platform.` 與 `* text eol=lf` |

### 目錄的狀態（`check` 的 `export_dir`）

| 值 | 判定 | 能否繼續 |
|---|---|---|
| `"none"` | 路徑不存在 | 可以（第一次匯出） |
| `"empty"` | 是空目錄 | 可以（寫入不會覆蓋任何東西；目錄不是本功能建立的，所以寫入失敗時不移除它） |
| `"ours"` | 目錄內只有上表的檔案（`README.md` 與 `.gitattributes` 可以缺少），`nutrients.json` 存在、是有效 JSON、`tool` 為 `"sdd-export"`、`schema` 不大於支援的版本，且通過驗證 | 可以（再次匯出） |
| `"conflict"` | 路徑是檔案；或目錄內有上表以外的項目；或沒有 `nutrients.json` 卻有其他檔案；或 `nutrients.json` 是有效 JSON 但 `tool` 不是 `"sdd-export"` | 不可以；結束碼 3 |
| `"unreadable"` | `nutrients.json` 不是有效的 UTF-8 JSON 物件 | 不可以；結束碼 3 |
| `"newer"` | `schema` 大於支援的版本 | 不可以；結束碼 3 |
| `"invalid"` | 結構不符合本文件，或字串、欄位名稱符合機密樣式（通常是手動編輯造成；006 寫入時已攔截機密樣式） | 不可以；結束碼 3，輸出違反的欄位路徑（機密樣式只輸出 `check: secret` 與路徑，不輸出內容） |

`.gitattributes` 的內容與上表不同時（維護者改過），`write` 不改寫它，`check` 以 `gitattributes: "edited"` 回報；
不存在時 `write` 建立它（`"missing"`）。它不影響目錄是否屬於本功能。

### 手動編輯的偵測（`check` 的 `nutrients`、`view`）

`README.md` 的第一行是標記：

```text
<!-- Generated by sdd-export from nutrients.json; do not edit. source-sha256: <64 hex> view-sha256: <64 hex> -->
```

- `source-sha256`：寫入時 `nutrients.json`（換行正規化後）的 SHA-256。
- `view-sha256`：`README.md` 第二行起的內容（換行正規化後）的 SHA-256。

| 欄位 | 值 | 判定 |
|---|---|---|
| `nutrients` | `"none"` | 沒有 `nutrients.json` |
| | `"unchanged"` | 雜湊等於標記的 `source-sha256` |
| | `"edited"` | 雜湊不同（手動編輯，或上次寫入在兩個檔案之間中斷） |
| | `"unknown"` | `README.md` 不存在或第一行不是標記 |
| `view` | `"none"` | 沒有 `nutrients.json` 也沒有 `README.md` |
| | `"current"` | 本文雜湊等於 `view-sha256`，且 `source-sha256` 等於目前的 `nutrients.json` |
| | `"stale"` | 本文沒被改，但 `source-sha256` 與目前的 `nutrients.json` 不同 |
| | `"edited"` | 本文雜湊不等於 `view-sha256`，或第一行不是標記 |
| | `"missing"` | 有 `nutrients.json`，沒有 `README.md` |

`check` 另外輸出 `view_secret_lines`：`README.md` 中符合機密樣式（見「機密樣式」）的行號，只有行號。`README.md` 由養分產生，
只有手動修改才可能出現命中；SKILL.md 階段 7 在它不為空時不讀取 `README.md`（請維護者自行移除那幾行，或放棄手動修改由 `write` 重新產生）。

### `state`

`check` 輸出的 `state` 是 `.sdd-export/nutrients.json` 與 `.sdd-export/README.md` 目前內容的雜湊
（各自換行正規化後的 SHA-256，以固定順序串接後再取 SHA-256；不存在的檔案以空字串代表）；兩者都不存在時是 `"none"`。
`write --expect <state>` 以它確認寫入前的內容與 Claude 比對差異時相同。

## 養分（`nutrients.json`）

### 頂層

| 鍵 | 型別 | 填入者 | 說明 |
|---|---|---|---|
| `tool` | `"sdd-export"` | 腳本 | 歸屬 |
| `schema` | `1` | 腳本 | 格式版本 |
| `generation` | 整數 ≥ 1 | Claude（腳本驗證） | 匯出它的專案的世代，MUST 等於 `check` 的 `generation` |
| `project` | 字串 | Claude | 專案的顯示名稱（通常是目錄名稱）；MUST NOT 含 `/`、`\` 或機器專屬路徑 |
| `exported_at` | `"YYYY-MM-DD"` | 腳本 | 寫入當天的 UTC 日期 |
| `language` | `"zh-Hant"` | Claude（腳本驗證） | 字串內容的語言；schema 1 固定為此值 |
| `scope` | 物件 | Claude | 見下 |
| `principles` | 陣列 | Claude | 原則，可以是空的（專案沒有 constitution、也沒有導出原則時） |
| `features` | 陣列 | Claude | 功能，依相依順序（被依賴的在前）；至少一個 |
| `lessons` | 陣列 | Claude | 經驗教訓，可以是空的（US3-3：找不到且維護者不補充） |
| `discarded` | 陣列 | Claude | 捨棄紀錄，可以是空的 |

### `scope`

| 鍵 | 型別 | 說明 |
|---|---|---|
| `coverage` | `"full"` 或 `"partial"` | 是否涵蓋整個專案 |
| `included` | 路徑陣列 | `partial` 時涵蓋的區塊（至少一個，MUST 存在）；`full` 時是空陣列 |

### 共通的項目欄位

原則、功能、需求、教訓都有以下欄位（順序即序列化順序，各自特有的欄位接在 `id`、`origin` 之後，見各節）：

| 鍵 | 型別 | 說明 |
|---|---|---|
| `id` | 識別字 | 整份養分中唯一；跨世代不變 |
| `origin` | 整數 | 首次出現的世代，1 ≤ `origin` ≤ `generation`；小於 `generation` 即為繼承 |
| `revised` | 整數陣列 | 內容被修改過的世代，嚴格遞增，每個值 > `origin` 且 ≤ `generation`；可以是空的 |
| `derived_from` | 識別字陣列 | 由前代哪些項目合併或拆分而來；可以是空的 |
| `status` | `"confirmed"` 或 `"pending"` | `pending` 即「待確認」 |
| `evidence` | 字串陣列 | 依據，見下；`confirmed` 時至少一筆，`pending` 時可以是空的 |

功能本身沒有 `status` 與 `evidence`（由它的需求承載），見「功能」。

### 依據（`evidence` 的每一筆）

| 形式 | 驗證 |
|---|---|
| 相對路徑（檔案或目錄） | 存在於專案；不是機密檔案；不在排除範圍（見「讀取範圍」）。世代紀錄 `.sdd-rebuild/lineage.json` 與 `.specify/memory/constitution.md` 允許 |
| `commit:<7 至 40 位小寫十六進位>` | 專案是 git repository，且 `git cat-file -e <hash>^{commit}` 成功 |
| `maintainer` | 維護者在這次對話中口頭提供 |

### 原則（`principles[]`）

`id`、`origin`、`title`（字串）、`text`（字串，原則的完整內容，可含多行）、`revised`、`derived_from`、
`source`（`"constitution"`、`"doc"`、`"code"`、`"maintainer"`）、`status`、`evidence`。

### 功能（`features[]`）

| 鍵 | 型別 | 說明 |
|---|---|---|
| `id`、`origin` | | 共通 |
| `title` | 字串 | 功能名稱 |
| `summary` | 字串 | 一段話描述使用者能做什麼 |
| `revised`、`derived_from` | | 共通 |
| `source` | `"spec"`、`"code"`、`"mixed"`、`"maintainer"` | `mixed`：spec 只涵蓋部分，其餘從程式碼導出（US2-4） |
| `spec` | 路徑或 `null` | 來源 spec（例如 `specs/003-sdd-init/spec.md`）；`source` 為 `spec` 或 `mixed` 時 MUST 是存在的檔案 |
| `depends_on` | 識別字陣列 | 依賴的功能 `id`；MUST 指向排在它前面的功能（因此沒有循環） |
| `requirements` | 陣列 | 至少一個 |

### 需求（`features[].requirements[]`）

`id`、`origin`、`kind`、`text`、`revised`、`derived_from`、`source`、`status`、`evidence`。

| 鍵 | 值 |
|---|---|
| `kind` | `"story"`（使用情境與驗收情境）、`"functional"`（功能需求）、`"edge-case"`、`"success-criterion"`、`"assumption"` |
| `text` | 使用者需求或可驗收的行為；不描述實作（FR-004）；可含多行 |
| `source` | `"spec"`、`"code"`、`"doc"`、`"maintainer"` |

### 經驗教訓（`lessons[]`）

`id`、`origin`、`kind`、`title`、`text`、`revised`、`derived_from`、`status`、`evidence`。

| 鍵 | 值 |
|---|---|
| `kind` | `"decision"`（重要決定與理由）、`"pitfall"`（踩過的坑）、`"reversed"`（被推翻的做法） |
| `text` | 內容；`decision` 要含理由，`reversed` 要含推翻的原因 |

### 捨棄紀錄（`discarded[]`）

| 鍵 | 型別 | 說明 |
|---|---|---|
| `id` | 識別字 | 被捨棄項目的 `id`；捨棄的疑點由 Claude 取新的 `id` |
| `kind` | `"principle"`、`"feature"`、`"requirement"`、`"lesson"`、`"doubt"` | |
| `origin` | 整數 | 該項目的 `origin`；疑點為發現它的世代 |
| `discarded_in` | 整數 | 被捨棄的世代，`origin` ≤ `discarded_in` ≤ `generation` |
| `text` | 字串 | 被捨棄的內容（摘要即可） |
| `reason` | 字串 | 維護者給的理由；沒有說明時寫「維護者決定捨棄」 |

### 草稿（`validate`、`write` 的 stdin）

與養分相同，但**不含**腳本填入的 `tool`、`schema`、`exported_at`（含有時拒絕，避免 Claude 以為可以指定）。
其餘鍵全部必填，順序不拘（腳本依上面的順序重新序列化）。

## 世代紀錄（`lineage.json`）——**007 sdd-rebuild 寫入、006 讀取的契約**

位置：新專案根目錄的 `.sdd-rebuild/lineage.json`，MUST 提交到 repo。`.sdd-rebuild/` 只屬於 sdd-rebuild；
006 只讀 `lineage.json`，不讀也不寫該目錄中的其他檔案。序列化規則同上。

### 頂層

| 鍵 | 型別 | 說明 |
|---|---|---|
| `tool` | `"sdd-rebuild"` | 歸屬 |
| `schema` | `1` | 格式版本 |
| `generation` | 整數 ≥ 2 | 這個專案的世代 = `source.generation` + 1 |
| `rebuilt_at` | `"YYYY-MM-DD"` | 重建當天的 UTC 日期 |
| `source` | 物件 | `{"project": <來源養分的 project>, "generation": <來源養分的 generation>, "nutrients_schema": <來源養分的 schema>}` |
| `principles` | 陣列 | 重建時確認的原則 |
| `features` | 陣列 | 重建時確認的功能，依產生 spec 的順序 |
| `lessons` | 陣列 | 重建時確認仍然適用的教訓 |
| `discarded` | 陣列 | 來源養分的 `discarded` 全部，加上重建時捨棄的項目 |

### 項目

與養分的同名項目相同，**去掉 `status` 與 `evidence`**（重建時待確認的項目已由維護者逐項決定，007 FR-018），另外：

- 功能多一個 `spec_dir`（緊接在 `source` 之後）：這個功能在新專案產生的 spec 資料夾（例如 `specs/002-deploy`），
  MUST 是 `specs/` 底下的一層資料夾。`spec` 欄位在世代紀錄中是來源養分的值（舊專案的路徑，只作追溯，不要求存在）。
- 功能的 `source` 在世代紀錄中可以多一個值 `"rebuild"`：重建時新增的功能。需求、原則的 `source` 同樣可以是 `"rebuild"`。
- 捨棄紀錄的結構與養分相同。

### 007 寫入時 MUST 遵守的規則

| 情況 | `id` | `origin` | `revised` | `derived_from` | 其他 |
|---|---|---|---|---|---|
| 原樣保留 | 沿用 | 沿用 | 沿用 | 沿用並補入祖先（見表後） | |
| 修改後保留 | 沿用 | 沿用 | 沿用並加上 `generation` | 沿用並補入祖先（見表後） | |
| 合併多個項目 | 新取（見表後） | `generation` | 空 | 被合併的 `id`，並補入祖先（見表後） | 被合併的項目不必另記為捨棄 |
| 拆分一個項目 | 新取（見表後） | `generation` | 空 | 被拆分的 `id`，並補入祖先（見表後） | 原項目可以同時依「原樣保留」或「修改後保留」保留 |
| 重建時新增 | 新取（見表後） | `generation` | 空 | 空 | `source` 為 `"rebuild"` |
| 捨棄 | 沿用 | 沿用 | | | 移到 `discarded`，`discarded_in` 為 `generation` |
| 來源養分的 `discarded` | 沿用 | 沿用 | | | 原樣帶入 |
| 來源養分中 `pending` 的項目 | 依維護者的決定套用上面任一列 | | | | 不得以 `pending` 寫入 |

「新取」的 `id` MUST NOT 與來源養分的任何有效項目、`discarded` 中的任何 `id`，或來源養分任何項目的 `derived_from` 中出現過的
`id` 相同，也不與世代紀錄中其他項目的 `id` 相同：被合併或拆分而消失的 `id` 仍代表前代的那個項目，重複使用會讓追溯同時指向
兩個不同的項目（世代規則 9）。

「補入祖先」：007 以來源養分的所有有效項目，以及舊專案的 `.sdd-rebuild/lineage.json`（存在、通過驗證且世代與養分相同時）的所有有效項目，
建立「`id` → `derived_from`」的祖先表（同一個 `id` 兩邊都有時取聯集，養分的在前）。寫入的 `derived_from` 是：直接來源依序在前
（保留與修改的項目是祖先表中它自己的清單，合併與拆分的項目是被合併或被拆分的 `id`），接著依直接來源的順序，把每個直接來源在祖先表中的
`derived_from` 依記錄的順序深度優先展開；去重，保留第一次出現的位置。如此一來，經過合併再拆分的項目仍記得最早的來源，
那些 `id` 留在世代紀錄中而被世代規則 9 擋下重用；世代規則 8 允許沿用世代紀錄已記下的來源，世代規則 5 只比較內容欄位，
所以補入後變長的 `derived_from` 不影響下一次匯出。

已知限制（維護者接受，2026-11-20）：捨棄紀錄沒有 `derived_from`，被捨棄項目的來源只保留到該次捨棄為止（被捨棄的項目本身仍在
`discarded`，不能重用）；匯出時的合併或拆分只記下直接來源（世代規則 8 不允許在匯出時補入），下一次重建由舊專案的世代紀錄補上，
但同一代內第二次匯出合併了第一次匯出才建立的項目時，第一次匯出記下的來源會遺失。

來源養分中的每一個有效項目 MUST 對應到上表其中一列（保留、修改、被合併或拆分到某個新項目的 `derived_from`、或捨棄），
否則 006 下一次匯出時會以世代規則 2 拒絕。

### 006 讀取時的驗證（`check` 的 `lineage`）

| 值 | 判定 | 能否繼續 |
|---|---|---|
| `"none"` | `.sdd-rebuild/lineage.json` 不存在 | 可以；這一代是 1 |
| `"present"` | 有效、`tool` 為 `"sdd-rebuild"`、`schema` 受支援、通過結構驗證與上表可檢查的部分（`generation` = `source.generation` + 1、`origin` 與 `revised` 的範圍、`id` 唯一、`depends_on` 在前），且沒有符合機密樣式的字串或欄位名稱 | 可以；這一代是紀錄的 `generation` |
| `"unreadable"`、`"newer"`、`"invalid"`、`"conflict"`（`tool` 不符） | 同專用目錄的定義 | 不可以；結束碼 3 |

## 世代規則（`validate` 對照世代紀錄 L 與既有養分 N）

「前代的項目」指 L 中所有有效項目（`principles`、`features`、`requirements`、`lessons`），以及 N 中 `origin` 小於 `generation` 的有效項目。

| 編號 | `check` 名稱 | 規則 |
|---|---|---|
| 1 | `generation` | 草稿的 `generation` 等於 `check` 的 `generation` |
| 2 | `lineage-item-missing` | L 中每個有效項目的 `id`，在草稿中仍是有效項目、在草稿的 `discarded` 中，或出現在草稿某個項目的 `derived_from` |
| 3 | `origin-changed` | 與前代項目同 `id` 的有效項目，`origin` 相同 |
| 4 | `origin-unknown` | `origin` 小於 `generation` 的項目，`id` 能在 L 或 N 中找到 |
| 5 | `revision-unmarked` | 與 L 中同 `id` 的項目相比，`title`、`text` 或 `summary` 不同時，`revised` 包含 `generation`。只適用於 `origin` 小於 `generation` 的項目（繼承的項目）；`origin` 等於 `generation` 的項目是這一代建立的，不檢查，`revised` 也不允許包含這一代（範圍規則已保證 `revised` 的每個值大於 `origin`） |
| 6 | `discard-lost` | L 的 `discarded`，以及 N 中 `discarded_in` 小於 `generation` 的捨棄紀錄，都原樣出現在草稿的 `discarded` |
| 7 | `discarded-active` | `discarded` 中的 `id` 不是有效項目 |
| 8 | `derived-unknown` | `derived_from` 中的每個 `id` 出現在 L 或 N（含其 `discarded`），或已出現在 L、N 中同一項目的 `derived_from`（沿用前代記下的來源，那些 `id` 屬於更早的世代，不在 L 中） |
| 9 | `id-reused` | `origin` 等於 `generation` 的項目，`id` 不與 L 中任何項目（含 `discarded`）相同，也不與 L、N 中任何項目的 `derived_from` 出現過的 `id`（曾經存在、後來被合併或拆分而不再是有效項目的 `id`）相同。沿用不算重用：L 中同 `id`、同種類、`origin` 也等於這一代的有效項目（重建時新增、合併或拆分而建立的項目）視為沿用；只出現在 `derived_from` 的 `id`，另外與 N 中同 `id`、同種類、`origin` 也等於這一代的有效項目（這一代先前的匯出寫入、仍然有效的項目）相同時也視為沿用。違反的情況是 `id` 與 L 的 `discarded` 相同、與 L 中 `origin` 不等於這一代（或種類不同）的有效項目相同，或與 `derived_from` 中出現過、而不屬於上述沿用的 `id` 相同。直接後果：被合併的項目之後不能以原來的 `id`「拆回去」，拆出的項目 MUST 取新的 `id`，並以 `derived_from` 指向合併後的項目 |

## 驗證規則（`validate`）

除上表外，`validate` 依序檢查（`check` 名稱用於輸出的 `errors[].check`）：

| `check` 名稱 | 規則 |
|---|---|
| `json` | stdin 是有效的 UTF-8 JSON 物件 |
| `field` | 鍵齊全、沒有多出的鍵、型別與列舉值正確（含不得出現 `tool`、`schema`、`exported_at`） |
| `id` | 格式正確且整份唯一 |
| `range` | `origin`、`revised`、`discarded_in` 的範圍 |
| `code-block` | 字串中沒有程式碼區塊 |
| `secret` | 字串不符合機密樣式（見「機密樣式」）；只輸出欄位路徑 |
| `evidence` | 每一筆的形式正確且存在；不指向機密檔案或排除的路徑 |
| `unsupported` | `confirmed` 的項目至少有一筆依據 |
| `spec` | `source` 為 `spec` 或 `mixed` 的功能，`spec` 是存在的檔案 |
| `dependency` | `depends_on` 指向排在前面的功能 |
| `scope` | `partial` 時 `included` 非空且每一項存在；`full` 時為空 |

所有錯誤一次列出（不在第一個錯誤就停止），依欄位路徑排序。

## 差異（`validate` 輸出的 `diff`）

既有養分存在時，以 `id` 對照草稿（正規化後）與既有養分：

| 鍵 | 內容 |
|---|---|
| `base` | `"none"`（沒有既有養分，所有項目都是新增）或 `"nutrients"` |
| `generation` | `{"from": <既有>, "to": <草稿>}`；相同時是 `null` |
| `scope` | 有改變時是 `{"from": ..., "to": ...}`；否則 `null` |
| `added` | `[{"section": ..., "id": ..., "title": ...}]`；`section` 為 `principles`、`features`、`requirements`、`lessons`、`discarded` |
| `removed` | 同上 |
| `changed` | `[{"section": ..., "id": ..., "fields": [{"field": ..., "from": ..., "to": ...}]}]`；需求的 `id` 不變但移到另一個功能時，`field` 為 `"feature"` |
| `order_changed` | 功能的順序是否改變（布林） |

`title` 對沒有 `title` 的項目（需求）取 `text` 的第一行，最多 80 個字元。

## 讀取範圍（`check`、`files`）

| 類別（`skipped` 的鍵） | 規則 |
|---|---|
| `ignored` | 專案是 git repository 時，不在 `git ls-files -z --cached --others --exclude-standard` 結果中的檔案 |
| `dependency` | 任何一層的目錄名稱為 `node_modules`、`bower_components`、`jspm_packages`、`vendor`、`.venv`、`venv`、`Pods`、`Carthage`、`.terraform`、`.bundle` |
| `build` | 任何一層的目錄名稱為 `dist`、`build`、`target`、`bin`、`obj`、`out`、`.next`、`.nuxt`、`.svelte-kit`、`.output`、`coverage`、`htmlcov`、`__pycache__`、`.pytest_cache`、`.mypy_cache`、`.ruff_cache`、`.tox`、`.nox`、`.gradle`、`.cache`、`.parcel-cache`、`.turbo`、`.eggs`；或名稱以 `.egg-info` 結尾 |
| `tooling` | 頂層的 `.git`、`.idea`、`.vscode`、`.claude`、`.sdd-export`、`.sdd-rebuild`、`.specify`（例外：`.specify/memory/constitution.md` 可讀） |
| `generated` | 檔名為 `package-lock.json`、`yarn.lock`、`pnpm-lock.yaml`、`npm-shrinkwrap.json`、`uv.lock`、`poetry.lock`、`Pipfile.lock`、`Cargo.lock`、`go.sum`、`composer.lock`、`Gemfile.lock`、`packages.lock.json`；或以 `.min.js`、`.min.css`、`.map` 結尾 |
| `secret` | 見「機密檔案」；腳本不開啟 |
| `binary` | 副檔名屬於圖片、影音、字型、壓縮檔、執行檔與函式庫、資料庫檔、Office 與 PDF 文件；或開頭 8 KiB 含 NUL 位元組 |
| `large` | 大於 1 MiB |

比對以路徑的各段名稱進行，Windows 上同樣以 `/` 分隔、區分大小寫的規則比對小寫化後的名稱。
符號連結：指向專案外的一律略過（計入 `ignored`）；不跟隨目錄的符號連結（也計入 `ignored`）。

`skipped` 的計數：以目錄排除的類別（`dependency`、`build`、`tooling`）每個被排除的目錄算一次（不走進去逐檔計算，
`node_modules/` 這類目錄可能有數萬個檔案）；其餘類別每個檔案算一次。`ignored` 在 git repository 中是
`git ls-files --others --ignored --exclude-standard --directory` 列出的項目數（被忽略的整個目錄算一次），加上略過的符號連結。
兩個平台、有沒有 git（沒有 `.gitignore` 時）的計數都相同。

**過大**（`too_large`）：可讀檔案數 > 1500，或可讀檔案總大小 > 10 MiB，或有兩個以上的區塊在其頂層含有套件描述檔
（`package.json`、`pyproject.toml`、`setup.py`、`go.mod`、`Cargo.toml`、`pom.xml`、`build.gradle`、`build.gradle.kts`、
`*.csproj`、`*.sln`、`composer.json`、`Gemfile`、`mix.exs`、`pubspec.yaml`）。

**區塊**（`areas`）：頂層的每個目錄一個區塊（排除上表的目錄），頂層的檔案合為 `"."`；每個區塊列出可讀檔案數、
總大小與它頂層的套件描述檔。

### 機密樣式（掃描字串與可讀檔案）

掃描的對象：草稿（`validate`、`write`）、讀取時的既有養分與世代紀錄（字串值與欄位名稱；命中即為 `invalid`）、
`files` 的可讀檔案（`secret_hits`）與 `.sdd-export/README.md`（`view_secret_lines`）。

與 005 的 `SECRET_PATTERNS` 逐字相同（006 不載入 005，各自保存一份；`tests/unit/test_sdd_secret_patterns.py` 比對兩份的樣式文字，
並以同一組樣本確認兩邊的判斷逐一相同，任何一邊改了而沒有同步就會失敗）：

- `-----BEGIN [A-Z0-9 ]*PRIVATE KEY-----`
- `ghp_` 後接 20 個以上英數；`github_pat_` 後接 20 個以上英數或底線
- `sk-` 後接 20 個以上英數、底線或連字號；`xox[abpr]-` 後接 10 個以上英數或連字號；`AKIA` 後接 16 個大寫英數
- URL 中的 `user:password@`：`://` 前面那一段 scheme 字元（英數、`+`、`.`、`-`）中至少有一個英文字母即可，
  與 URL 前面接什麼字元無關（`步驟 1.https://…`、`[0].https://…` 也算）。樣式只從那一段字元的開頭比對，數 MB 的單行也維持線性時間
- `password`、`secret`、`token`、`api_key`（不分大小寫，`api-key`、`apikey` 亦同）後接 `=` 或 `:` 與一段非空白值

## 狀態轉移

本功能沒有進度，只有專用目錄的狀態：

```text
none / empty ──(確認後 write)──▶ ours（nutrients: unchanged, view: current）
ours ──(維護者手動編輯 nutrients.json)──▶ ours（nutrients: edited, view: stale）或 invalid（含加入機密樣式）/ unreadable
ours ──(維護者手動編輯 README.md)──▶ ours（view: edited）
ours ──(再次匯出，確認後 write)──▶ ours（unchanged, current）
invalid / unreadable / newer / conflict ──(維護者修正或移走)──▶ ours / none
```

`write` 從不刪除檔案；`.sdd-export/` 只由維護者自己刪除。
