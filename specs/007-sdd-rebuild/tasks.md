# Tasks: sdd-rebuild 在新專案以養分重建

**Input**: Design documents from `/specs/007-sdd-rebuild/`

**Prerequisites**: plan.md、spec.md、research.md、data-model.md、contracts/cli.md、contracts/skill.md、quickstart.md

**Tests**: 需要。Constitution（v1.0.2）原則 II 要求每個功能 MUST 有自動測試，且在 Windows 與 Linux 的 CI 上都通過才能合併。
腳本 `sdd_rebuild.py` 的每個指令（`check`、`save`、`preview`、`claim`、`verify`、`lineage`、`focus`、`clear`）先寫測試、確認失敗，再實作；
`SKILL.md` 與 `README.md` 以結構與內容檢查驗證（關鍵字與段落順序，不比對完整文字）。
測試指令是 `uv run --with pytest pytest`。

**Organization**: 依 user story 分組。這是**對話式的 skill**（與 003 不同，與 005、006 同類）：對話行為（逐項決定的品質、教訓調整的呈現、
確認前不寫入、矛盾的指出、中斷後的接續）無法在 CI 驗證，research.md R12 把每條 FR 對應到單元測試、結構／內容檢查或人工驗收。
本清單只為前兩類產生任務；只能人工驗收的部分見最後的 Notes，不列為勾選任務。
腳本的所有指令在同一支 `home/skills/sdd-rebuild/scripts/sdd_rebuild.py`，單元測試在 `tests/unit/test_sdd_rebuild.py`，
多代來回測試在 `tests/unit/test_sdd_rebuild_generations.py`，skill 的結構與內容檢查在 `tests/unit/test_sdd_rebuild_skill.py`；
改同一個檔案的任務依序進行。`SKILL.md` 的各階段由多個任務寫入同一個檔案：**段落依 contracts/skill.md 的階段編號排列，與任務的先後無關**；
每個 SKILL.md 任務都標明它負責 contracts/skill.md 的哪些條目與哪些「結果」列，並逐一列出該階段的每一種結果與它的下一步。

## Format: `[ID] [P?] [Story] Description`

- **[P]**: 可平行（不同檔案、沒有未完成的相依）
- **[Story]**: 所屬的 user story（US1 至 US4）；Setup、Foundational、Polish 階段不加 story 標籤
- 路徑相對於 repo 根目錄
- `contracts/skill.md 第 N 項` 指該文件「SKILL.md 的內文」中編號為 N 的條目（1 至 50）；
  `階段 N 的結果列` 指該階段表格中的每一列（成功、各種失敗、維護者改變主意、中途結束後接續）
- 引用 data-model.md 的欄位時寫作 `data-model.md` 的 `Entity.field`；Entity 名稱對應小節：`Progress`（進度的欄位表）、`Source`（快照）、
  `TargetItem`（目標的項目欄位）、`Discard`（`discards` 的項目）、`PreviewCheck`（`preview` 的檢查）、`Ancestors`（祖先表與補入）、
  `LineageCompose`（世代紀錄的組成）、`RebuildDir`（`.sdd-rebuild/` 的狀態）、`OwnFolder`（`.specify/sdd-rebuild/` 的規則）
- 006 契約指 `specs/006-sdd-export/data-model.md`；005、006 的函式名稱以實作時實際存在者為準（research.md R2），不存在或行為與設計文件不同時向主代理提問
